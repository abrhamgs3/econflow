## Task 1 — Diagnostics plugin system

**Investigation.** `BaseDiagnostic`/`register_diagnostic()`/`get_diagnostic()`/`list_diagnostics()` (`diagnostics/registry.py`, `diagnostics/base.py`) are real, tested code — not vaporware. Four plugins (`hausman`, `breusch_pagan`, `pesaran_cd`, `vif`) are fully implemented and covered by 25+ passing tests across `tests/unit/test_diagnostic_registry.py` and `tests/integration/test_diagnostic_run.py` (verified: real `EstimationResult` objects from `EntityFE`/`RandomEffects`/`PooledOLS` are fed into each plugin and the results checked). Two (`wooldridge`, `serial_correlation`) are self-declared `status="stub"` and correctly raise `NotImplementedError`, also tested. `hausman` and `pesaran_cd` have no equivalent anywhere else in the codebase — they are EconFlow's only implementation of those two tests. `vif` and `breusch_pagan` are independently duplicated in the live pipeline's `estimation/_diagnostics.py` (different calling convention: `data=`/`result.provenance` vs. the live path's pre-computed `result.extra`).

None of this is invoked by `pipeline_generic.py` or the dispatcher. `PLUGIN_SDK.md §4` claimed "the pipeline runs all registered diagnostics that declare support for the estimator used" and showed a `models.yaml` usage example with a `diagnostics:` key — **both false**: no config loader anywhere in `src/econflow/config/` parses a `diagnostics:` key, and `econflow run` never calls `get_diagnostic()`.

**Decision: (B) — mark experimental, correct the SDK.** Reasoning against the other two options: (A) wiring it into the runtime would change `diagnostics.csv`'s real output shape for every user — a functional/behavioral change to a release asset, not a documentation fix, and explicitly out of this session's scope ("NOT to redesign... or improve architecture"). (C) deprecating/removing would delete correct, tested, econometrically valid code — including the only implementation of Hausman and Pesaran CD in the project — which fails Rule 3 ("never replace working implementations") on code that isn't actually broken, just not yet integrated.

**Fix made:** `docs/sdk/PLUGIN_SDK.md` — added an explicit "Status: experimental / library API, not wired into `econflow run`" notice to §4, corrected the fictitious `diagnostics:` config-key example to show the real, direct call pattern, and added a one-line exception note to §12.3 ("Runtime") so it no longer implies diagnostics are config-driven like estimators/connectors are. Zero runtime code touched.

## Task 2 — `numerical_results.json` / `diagnostics_full.json`

**Canonical generation path:** none exists. Grepped all of `src/econflow/` for the literal filenames — zero matches. No CLI command, pipeline step, or script in the repository produces these two files. They are purely test fixtures, hand-authored or generated by a one-off script that is not in the repository.

**Expected producer:** the only code that reproduces comparable numbers is `tests/integration/test_pipeline_baseline.py`'s own `pipeline_results()` fixture — and it does **not** call `econflow.estimation` at all. It builds `X` with an explicit `"const"` column and calls raw `linearmodels.PanelOLS(..., entity_effects=True, drop_absorbed=True)` directly. Confirmed live in this sandbox:

- Production `EntityFE.fit(...).params.index` → `['value', 'capital']` — no `const` (correct: the constant is collinear with the absorbed entity fixed effects).
- The test's own standalone reimplementation, with an explicit `const` column forced into `X` → `params.index` → `['const', 'value', 'capital']`, `const = -55.27...` — a value `linearmodels` is willing to report, but one `econflow run` never produces for a real user.

The module's own docstring claimed to "establish the numerical gate for the EstimationDispatcher migration" by comparing "the CURRENT pipeline output" — but the module never imports `econflow.estimation` or `pipeline_generic`. This is confirmed by grep (zero matches for `from econflow` / `import econflow` / any estimator class name in the file) and by the fact that all 154 tests in the file currently pass while testing something that isn't the production pipeline.

**Regeneration command:** none exists, and none was fabricated. Given there is no official producer, "regenerate through the official pipeline" isn't achievable for this pair of files as literally worded — doing so would require inventing new production tooling (a CI/infra addition), which is out of this session's scope.

**Stale?** Yes, relative to what `econflow run` actually outputs for FE models — but not "broken": every test that reads these files currently passes, and no CLI/user-facing path reads them.

**Fix made:** corrected the module docstring and the `pipeline_results()` fixture's docstring in `test_pipeline_baseline.py` to state plainly what the fixture does and does not verify (a fixed `linearmodels` reference computation, not the production pipeline), including a direct pointer to the live evidence above. No JSON fixture values were touched — no hand-editing, and no fabricated "official" regeneration. Re-verified: 154/154 tests in the file still pass.

**Flagged for the maintainer, not fixed this session:** this "Phase 0 baseline" module's actual purpose (catching dispatcher migration regressions) has a genuine blind spot for FE constant-term handling, because it never exercises the real `EntityFE`/`TwoWayFE` classes. Closing that gap would mean rewriting the fixture to call production estimators directly and dropping `const` assertions for `entity_fe`/`twoway_fe` — a non-minimal change affecting dozens of parametrized assertions, deferred to a dedicated follow-up rather than done as a same-session, insufficiently-reviewed rewrite.

## Task 3 — Reproducibility, clean checkout

Set up a `git worktree` at the current commit, did a fresh `pip install -e .`, and ran the full documented chain.

- `econflow init` — works, scaffolds a project correctly.
- `econflow validate --config config/config.yaml` (getting_started example) — all four validation stages pass.
- `econflow run` — ran twice independently on the Grunfeld example; `sha256sum` of `diagnostics.csv`, `table_fe_investment.csv`, `table_fe_investment.tex` were **identical** across both runs. Deterministic.
- `econflow release-check --quick` — 6/6 non-slow checks passed (QG-01/06/07 are explicitly slow — package build, full integration suite, blind-replication reproduce — and exceed this sandbox's per-call time budget; QG-06 is literally `pytest tests/integration/`, already exhaustively re-run separately this and prior sessions with zero failures).

**A real, severe bug was found and fixed: `econflow reproduce` never actually reproduced anything.**

Root cause: `src/econflow/cli.py` had no `if __name__ == "__main__": app()` guard. `econflow.replication.planner._econflow_cmd()` invokes the CLI as `[sys.executable, "-m", "econflow.cli"]` — deliberately, per its own docstring, specifically to work around Windows PATH issues with the installed console-script. Without the guard, that invocation silently imports the module (defining the Typer `app` but never calling it) and exits 0, having done nothing. Confirmed directly: `python -m econflow.cli --help` produced zero output and exit code 0.

Consequence: every subprocess step `econflow reproduce` runs (`validate`, `run`) was a fake success. `reproduce` always reported PASS without the pipeline ever actually re-executing. This is the exact guarantee this task asked to verify, and it was silently false. It went undetected because every existing CLI test uses Typer's in-process `CliRunner` (`tests/replication/test_cli_replication.py`'s own docstring: "Uses Typer's test runner to avoid subprocess overhead") — nothing in the test suite exercises the real `-m econflow.cli` subprocess path. A second, independent piece of evidence for the same root cause: `commands/release_check.py`'s `check_cli_smoke()` (QG-03) already had a defensive fallback for this exact symptom ("if r_ver.returncode != 0 or not r_ver.stdout.strip(): # also try the entry-point binary") — but misattributed the cause to "Typer version callback writes via Rich, not always captured" rather than the missing `__main__` guard, and that fallback only covers `--version`/`doctor`, not `reproduce`'s `validate`/`run` steps.

**Fix:** added the two-line `if __name__ == "__main__": app()` guard to the end of `cli.py` — the minimal possible change; nothing else in the file was touched.

**Verification:**
1. `python -m econflow.cli --help` now prints the real, correct help text.
2. Re-ran `econflow reproduce examples/blind_replication/` end-to-end: the pipeline now genuinely re-executes (confirmed by real, non-trivial elapsed time and real output files, not instant/empty), and the comparison step performed a real diff — which surfaced a second, previously-invisible finding: `examples/blind_replication/original_outputs/tables/comparison_table.csv` had stale 3-decimal standard-error formatting (`(0.006)`) against the current renderer's 4-decimal output (`(0.0059)`) — same underlying numbers, not a scientific regression, confirmed by inspecting both files side by side. Regenerated that one file from a real `econflow run` (not hand-edited) and re-verified: `econflow reproduce` now reports **PASS** with a genuine 8-row, zero-diff comparison (`max |Δ| = 0.00e+00`), not the vacuous "no baseline to compare" skip it had been silently falling back to.
3. Re-ran `tests/replication/` + `tests/unit/test_cli_discoverability.py` + `tests/unit/test_first_user_experience.py`: 148/148 passed.

## Task 4 — Cross-platform verification

Static analysis only — this sandbox is Linux-only and cannot execute a Windows/macOS test run; this limitation is stated rather than papered over.

- No hardcoded `/dev/null` anywhere in `src/`.
- No hardcoded path-separator string-building (`os.sep`, literal `\\`) anywhere in `src/`.
- `pathlib.Path` used pervasively for file operations across every module inspected.
- All `fsync`-based atomic writes (`provenance.py`, `integrity/certificate.py`, `integrity/drift.py`, `ingestion/manifest.py`) explicitly declare `encoding="utf-8"`.
- `cli.py` already reconfigures `stdout`/`stderr` to UTF-8 on Windows before first console use (pre-existing "F1 fix"), addressing the classic cp1252 `UnicodeEncodeError` on stock Windows terminals.
- **Confirmed via this session's own CI config read** (`.github/workflows/ci.yml`): all three jobs (`test`, `lint`, `latex-compile`) run on `ubuntu-latest` only. There is no Windows or macOS runner. Cross-platform compatibility is therefore genuinely unverified by CI, not just by this sandbox — this is a real, confirmed gap, not a hedge.
- The Task 3 bug (`cli.py`'s missing `__main__` guard) is itself a cross-platform finding: it was specifically the Windows-PATH-portability code path that was broken, and it's now fixed.

## Task 5 — Dependency audit

`pyproject.toml` required dependencies: `pandas`, `numpy`, `statsmodels`, `linearmodels`, `matplotlib`, `scipy`, `typer`, `rich`, `pyyaml`, `pydantic` — all core to every estimator/pipeline path, correctly required (not optional).

Optional dependencies (`requests` for FRED/World Bank/IMF connectors, `openpyxl` for the Penn World Tables connector, `pyarrow` for parquet support) are **not** declared in `[project.optional-dependencies]` as a named extras group, but every one of them is imported lazily (inside a method, never at module top level — grepped for unguarded top-level imports of `requests`/`openpyxl`/`pyarrow`/etc.: zero matches) and wrapped in `try/except ImportError` that raises a clear `ConnectorError` with an exact `pip install <name>` instruction. This is confirmed correct behavior, not a gap: `commands/release_check.py`'s QG-02 (`check_package_import`) independently verifies all 9 top-level sub-packages import cleanly — this passed in this session's `release-check --quick` run, meaning `econflow` genuinely does not crash on import even without these optional libraries installed.

No install-instruction claim in the docs describes a currently-nonexistent extras group as already working — the one mention of a future `[project.optional-dependencies].excel = ["openpyxl>=3.1"]` extras group is in `docs/roadmap/ROADMAP_TO_V1.md`, explicitly a forward-looking roadmap document, not a claim about current state.

**No fix needed or made** — this area is clean.

## Task 6 — CI integrity

Read `.github/workflows/ci.yml` directly (not assumed from a prior report). Current state:

- `test`: `pytest tests/ -q --tb=short` on Python 3.10/3.11/3.12, `ubuntu-latest` only.
- `lint`: `ruff check src/ tests/`.
- `latex-compile`: compiles the expected LaTeX output on `ubuntu-latest`.

**Gaps, each with a concrete, minimal proposed check (not implemented this session — infra changes are out of scope beyond what a specific task explicitly authorized):**

1. **No Windows/macOS runner.** Proposed: add a `windows-latest` job running at minimum `pytest tests/replication/ tests/unit/test_cli_discoverability.py` plus a real `python -m econflow.cli --version` subprocess smoke check — the latter specifically because Task 3 found that exact invocation path had a silent, months-long failure mode that nothing in the existing suite (all in-process `CliRunner`-based) could catch.
2. **`econflow release-check` is never run in CI.** The repository built a 9-check release quality gate (`release_check.py`) that CI never invokes. Proposed: add it as a CI job (`econflow release-check` without `--quick`, budget permitting, or `--quick` plus a separate scheduled/nightly full run for the three slow checks).
3. **No fixture-freshness check.** Nothing in CI re-runs the example pipeline and diffs it against committed `expected_outputs/`/`baseline/`/`original_outputs/` fixtures. This is precisely the gap that let `examples/blind_replication/original_outputs/tables/comparison_table.csv` silently drift out of date (Task 3) and that left `numerical_results.json`/`diagnostics_full.json` stale for an unknown period (Task 2) — both were only caught by manual, session-level investigation. Proposed: a CI step that runs `econflow reproduce` against every example with a committed `original_outputs/`, failing the build on any diff.
4. **No documentation-claims check.** The `PLUGIN_SDK.md` §4 error (Task 1) — a written claim about runtime behavior that was simply false — went uncaught for at least one prior audit cycle. Proposed: even a lightweight test that imports every module path named in `PLUGIN_SDK.md`/`CLI_GUIDE.md` and asserts the documented surface actually exists/behaves as described would have caught both this and the `reproduce` docstring gap from the prior session.

## Deliverable 6 — Final recommendation

**READY AFTER MINOR FIXES**

Evidence: this session found and fixed one genuine, previously-undetected functional bug (`econflow reproduce` was a silent no-op) — exactly the kind of defect this protocol exists to catch, and it was caught, root-caused, minimally fixed, and re-verified with a real end-to-end pass. Recommended minimum before a clean READY verdict: land at least one of the Task 6 CI recommendations — ideally the subprocess-level CLI smoke test, since it directly closes the exact gap this session's fix exploited.
